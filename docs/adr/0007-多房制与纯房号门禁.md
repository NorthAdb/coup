# 多房制与纯房号门禁

本 ADR 修订 ADR-0004 的「不做多房制」条款；房间号仍是互联网联机的弱门禁，但服务端不再限制为单房。

## 背景

ADR-0004 为公网入口选择了纯房号加入、4 位房间号和失败查询限速，同时决定同一时刻只保留一房。实际产品需要让多桌并行开局，但仍不希望引入房间列表、账号体系或邀请链接主流程。现有实现的全局 `activeMatch`、`activeRoomCode`、单行 `lan_active_room`、裸座位 presence 键和全局单 run 保护，都会使第二房间覆盖或中止第一房间。

## 决策

- **推翻单房制**：服务器允许多个房间并行存在；本 ADR 明确修订 ADR-0004 的「不做多房制」条款。一个房间同一时刻仍至多承载一局对局，房间与对局继续是不同概念。
- **保持纯房号制**：产品仍为主机建房、生成 4 位房间号、客人凭号加入；不提供房间列表、大厅浏览或邀请链接主流程。一个浏览器同一时刻只处于一个房间，座位凭证保持单值。
- **容量与生命周期**：并发上限为 10 房。创建前先惰性回收满足条件的闲置房，再检查上限；仍满时返回 HTTP `503` 和 `room_capacity_reached`。空房定义为没有有效人类座位：lobby/rematch 无 `local_human` 或 `remote_human`，match 中除本地人类外的远程人类均为 `absent` 或 `timed_out`；`reconnecting` 宽限期不算空房。连续闲置 30 分钟回收并立即释放房间号。参数集中为服务端常量配置；建房暂不单独按 IP 限速。
- **房间作用域运行时与 API**：运行时采用 `Map<roomCode, ActiveMatch>`，所有开局、决策、轮询、tick、终局和离席处置按房号取值。对局端点改为 `GET /api/rooms/:code/matches/current` 与 `POST /api/rooms/:code/matches/current/decision`，不保留全局 URL 或凭据反查房间。
- **presence 隔离**：tracker 使用 `roomCode:seatId` 复合键；普通操作传入房号并只投影当前房间的裸座位号。全局 `clear()` 改为 `clearRoom(roomCode)`，仅进程级销毁可用 `clearAll()`。
- **移除单 run 不变量**：不同房间可同时有进行中的 run；`onCreated`、技术中止、恢复和续局只操作当前房间的 `matchId`，不得因第二房开局 abort 第一房。
- **房间表化持久化**：将 `lan_active_room` 改为按 `room_code` 主键的房间表，保存完整房间 payload 及 `created_at`、`updated_at`。`match_runs` 增加非空 `room_code` 和 `(room_code, run_status, updated_at)` 索引；`RoomRecord.matchId` 保留为快速指针和一致性校验。
- **逐房恢复与处置**：启动时全量读取房间并逐房恢复 lobby、rematch 或进行中的 match；恢复失败只标记该房，其他房继续服务。`/api/room-recovery/abandon` 必须携带 `roomCode`，只清理该房的 registry、持久化、运行时、presence 和失败状态。
- **建房不再拆房**：`POST /api/rooms` 不得解散旧房；它执行“先回收、再限额、最后新增”，失败房也计入容量，直到逐房 abandon 或生命周期回收。

## 备选

- **继续单房制**：被否决，无法满足两桌并行且会保留全局运行时、恢复和 presence 冲突。
- **房间列表/大厅浏览**：被否决；会改变纯房号产品边界，并暴露房间发现能力。客人仍只凭 4 位房间号加入。
- **邀请链接为主**：被否决；房间号仍是主入口，历史 `/join?code=####` 兼容不等于提供链接 UI。
- **每房独立应用实例或 tracker**：被否决；现有运行时可通过显式房间作用域复用，每房实例会扩大生命周期和注入改动面。
- **保留全局单 run 作为安全阀**：被否决；第二房开局会中止第一房，直接违反多房互不干扰。
- **环境开关控制多房或容量**：被否决；当前需要版本可审计、可测试的常量配置，不引入部署漂移。
- **建房立即按 IP 限速**：暂不采用；容量上限与空房回收先承担控制职责，观察滥用后再单独设计建房限速。
