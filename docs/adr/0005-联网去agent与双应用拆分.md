# 联网去 Agent 与双应用拆分

互联网联机版只承载真人多人对局；Agent 对战只在单机版存在。两块应用物理分离，代码不纠缠。

## 背景

MVP 是「本机人类 + 本机 Agent」对局，后来在同一应用里加入局域网房间，房间座位可配置为开放占座 / 本机 Agent / 关闭。产品转为互联网联机后明确：联网只玩真人（2–6 人），Agent 只在本机单机模式使用；部署到云服务器上的版本不得出现任何 Agent 痕迹（含「本机对战」入口）。

## 决策

- **房间流程纯真人**：座位只保留「开放占座 / 关闭」；删除大厅的 Agent 配置 UI、能力探测、开局门禁的「Agent 就绪」检查、离席处置里的「换本机 Agent」。开局门禁简化为：有效真人座位 2–6、无开放空槽；主机一人无法开局。
- **双应用拆分（monorepo）**：`apps/web` + `apps/server` 改造为纯联机版（部署到云）；新增 `apps/web-local` + `apps/server-local` 承载本机 Agent 对战（仅本机使用）。两版各自的应用代码零交叉：联机版没有 Agent 模块与本机对局路由，本机版没有房间/占座/离席/恢复代码。
- **正当共享层**：`packages/domain`（规则引擎）、`packages/protocol`（协议类型）原有；新增 `packages/web-desk` 承载与「Agent 还是多人」无关的策划桌 UI（对局桌、对局记录、节奏、规则面板）。服务端对局编排（matchRuntime 等）按版本各持一份，Agent 路径只存在于本机版副本。
- **不用分支、不用环境变量开关**：分支会让 domain/protocol 等共享层分叉、规则修复要跨分支同步；环境变量开关使同一文件内 if/else 纠缠，都不满足「代码不纠缠」。物理拆分为两个应用 + 明确共享层是三者里维护成本最低的。
- 域名入口下创建房间不再跳转（服务端已是主机模式且当前 Origin 被放行时直接在当前地址建房），局域网时代的「重绑跳转」逻辑只保留在本机版 loopback 场景。

## 备选

- 环境变量开关（同一构建两种形态）：被否决，纠缠。
- 分支分离：被否决，共享层分叉同步成本最高。
- 完全复制（零共享，对局桌也各一份）：隔离最彻底但 UI 改动双份维护，长期最贵。
