# 《政变》多房并行改造规格

## Problem Statement

联机版服务端按单房编排：全局「当前房间/当前对局」单例、单行房间持久化、裸座位号 presence 键、以及「开局即中止上一个进行中对局」的单 run 保护，会让第二个房间覆盖或中止第一个房间。产品需要多桌并行开局，同时保持纯房号制（无房间列表、一浏览器一房）。

## Solution

服务器同时承载最多 10 个互不干扰的房间。主机建房仍得 4 位房号，客人凭号加入，交互与现状完全一致；区别是建房不再解散旧房。每个房间拥有独立的对局运行时、在场追踪、持久化与重启恢复；一房失败不影响其他房。空闲房间自动回收以释放容量。该改造仅涉及联机版应用层，规则引擎与单机版不变。

## User Stories

1. 作为主机，我想创建房间并得到 4 位房号，以便口头分享给朋友加入（与现状一致）。
2. 作为主机，我想在已有房间仍在进行时创建第二个房间，以便并行主持两桌。
3. 作为主机，当并发房间达到上限时，我想看到「房间已满，稍后再试」的明确提示，以便理解建房失败而非困惑。
4. 作为主机，我想空闲房间自动解散并释放房号，以便不长期占用服务器容量。
5. 作为主机，我想空房计时在我或客人重新入座时重置，以便短暂离开不会被误回收。
6. 作为客人，我想凭 4 位房号加入任一存在房间（包括进行中的），以便加入朋友开的另一桌。
7. 作为客人，我想输错房号/房主未开房时得到与单房制相同的统一提示，以便不泄露房间是否存在。
8. 作为 A 房客人，我想我的心跳与离席状态只影响 A 房，以便两桌在场追踪互不干扰。
9. 作为主机，我想给 A、B 两房先后开局，以便两桌同时进行——B 房开局不得中止或影响 A 房对局。
10. 作为 A 房主机，我想对 A 房执行技术中止/强制淘汰等处置，以便不会误伤其他房间。
11. 作为 A 房玩家，我想跨房凭据无法读取或提交 B 房对局，以便多房隔离不被绕过。
12. 作为玩家，我想服务器重启后所有房间按各自阶段恢复（大厅/续局等待/进行中对局），以便继续原对局。
13. 作为主机，我想一房恢复失败只标记该房，其他房照常服务，以便不因单房损坏全部瘫痪。
14. 作为主机，我想放弃某个恢复失败的房间，以便清理后重开，且不影响其他房。
15. 作为客人，我想服务器重启后凭原座位凭证回席原房间，以便续上原对局。
16. 作为主机，我想续局等待（rematch）可在多个房间并行进行，以便各桌独立决定是否续局。
17. 作为部署者，我想容量与回收参数随版本内常量提供，以便行为可审计、可测试、可随发布调整。
18. 作为主机，我想房号保持 4 位数字，以便口头分享体验不变。
19. 作为客人，我想一个浏览器同一时刻只处于一个房间，以便凭证模型保持简单。
20. 作为主机，我想房间与对局数据按房间维度持久化，以便重启后按房间精确恢复。

## Implementation Decisions

- **运行时形态**：服务端应用编排层移除全局「当前房间/当前对局」单例，改为按房间号索引的进行中对局映射。开局、决策、轮询、心跳、在场 tick、离席处置、终局与技术中止一律先按房号取房间，再取该房的运行时；失败只清理该房条目。
- **对局 API 契约**：新增房间作用域对局端点 `GET /api/rooms/:code/matches/current` 与 `POST /api/rooms/:code/matches/current/decision`；废除全局当前对局端点，不做「凭据反查房间」。房间不存在与该房无对局分别返回对应错误。
- **建房契约**：`POST /api/rooms` 改为「先执行惰性闲置回收 → 校验并发上限 → 新增房间」，绝不解散任何旧房；达到上限返回 HTTP `503`、错误码 `room_capacity_reached`、提示「房间已满，稍后再试」。建房暂不单独按 IP 限速（复用现有房号失败查询限速的定位不变）。
- **presence 隔离**：座位在场追踪键从裸座位号改为「房间号 + 座位号」复合键；对外投影仍返回当前房间内的裸座位号，协议与 UI 不变。清理接口按房间维度提供；进程级全清仅用于显式销毁。开局、authority 恢复、终局、处置中的任何清理都不得波及其他房间。
- **移除单 run 不变量**：删除「开局即中止上一个进行中对局」的全局保护；不同房间可并存进行中对局。对局持久化回调改为只接收并处理当前房间；同房重开仍按既有门禁结束上一 run，跨房绝不作废。
- **数据模型**：房间持久化从单行表改为按 `room_code` 主键的房间表（完整房间 payload + `created_at` + `updated_at`）；对局运行表新增非空 `room_code` 列与 `(room_code, run_status, updated_at)` 索引；`RoomRecord.matchId` 保留为快速指针与恢复一致性校验，不作为唯一关联来源。
- **迁移**：启动时一次性迁移——旧单行房间数据解析校验后按房号入新表（损坏则保留旧行并报告启动级迁移失败，不静默丢数据）；旧对局运行按旧房间的 matchId 回填 `room_code`，无法归属的标记迁移异常且不得恢复；回填校验通过后收紧新写入为非空。
- **恢复语义**：启动全量读取房间并逐房恢复——大厅房直接恢复；续局等待房校验已结束的 matchId 后恢复；进行中房要求 run 存在、房号一致、`in_progress`，恢复原对局且不创建新 run。恢复失败房独立标记（含房号、原因、可展示摘要），其他房继续启动。恢复与放弃接口按房号工作：放弃一房不得 dissolve、清空或重置其他房。
- **生命周期**：服务端常量集中配置 `MAX_ROOMS = 10`、空闲回收 `30` 分钟，不读环境变量。空房定义：无有效人类座位——大厅/续局等待无本地或远程人类；进行中时本地人类恒有效、相关远程人类全部进入 `absent`/`timed_out` 才算空，`reconnecting` 的 15 秒宽限不算。空房连续闲置 30 分钟解散并释放房号；状态变更、占座/回席、续局与成功对局命令刷新活动时间，只读查询不延长。回收进行中房时，其进行中 run 以 `room_idle_reclaimed` 技术中止，避免遗留孤儿 run。
- **前端**：房间号已存在于请求路径与状态中，对局轮询与决策请求补齐房号即可；不新增前端多房状态模型，座位凭证单值保持不变。
- **领域词汇**：维持「房间 ≠ 对局」；多房不改变任何既有术语（大厅、占座、离席/回席、续局等待、座位凭证）。

## Testing Decisions

- **好测试的定义**：只测外部行为——通过 HTTP 请求与响应断言产品行为（建房、限额、开局、决策、心跳、恢复、放弃），不断言内部实现细节（如映射结构）；持久化测试只断言读写结果与迁移结果，不越过 SQL 表面。
- **主缝（最高缝）**：HTTP API 层——应用工厂注入临时 SQLite 与可控时钟，用 `app.inject()` 走完整请求路径。覆盖：两房并发开局互不干扰（第二房开局不中止第一房）、跨房凭据隔离（A 房座位码不可读写 B 房对局）、建房限额与惰性回收、逐房恢复与逐房放弃、presence 房间作用域（心跳/离席/终局清理不波及其他房）。
- **副缝**：持久化层——仅测迁移（旧单行房间表 → 新表；旧运行回填 `room_code`；损坏/无法归属的处置）与按房间查询（同房至多一个进行中、不同房间并存）。
- **被测试模块**：服务端应用（房间/对局/在场/恢复 API）、房间持久化、对局持久化。前端不设新缝（仅 URL 拼接），以服务端验收兜底 + 手动双浏览器验证。
- **先例**：`roomApi`、`roomRecoveryApi`、`absenceApi`、`sessionSeatApi`、`lobbyStartApi`（HTTP 层注入测试）；`matchStore`、`roomStore`（SQLite 与损坏注入测试）。新测试沿用同一模式。

## Out of Scope

- 房间列表/大厅浏览、邀请链接主流程、账号体系、公网匹配服。
- 一个浏览器同时处于多个房间、多标签各开一房，以及建房后换房的凭证迁移 UX。
- 跨房通信、聊天、观战、多房管理后台。
- 局域网单机版、本机 Agent 路径、`packages/domain` 规则引擎。
- 恢复失败房的复杂 UX 设计；本规格只要求逐房状态与逐房放弃 API。
- 建房按 IP 限速（由容量上限与闲置回收先承担控制职责，观察滥用后单独设计）。
