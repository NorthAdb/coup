# ADR-0011: 璀璨宝石（Splendor）接入平台栈

日期：2026-09-05
状态：已采纳

## 背景

平台层（ADR-0010）落地后，接入新桌游应当只写「规则适配器」而不碰房间编排。
《璀璨宝石》作为第三款游戏接入，用于验证 GameModule 接缝的完备性：
它的决策模型（原子命令）、终局语义（15 分后打完当前轮）、贵族多选与弃牌
待决阶段，都与 coup（响应窗口）和 brass（多步行动）不同。

## 决策

1. **规则引擎独立成包** `packages/splendor-domain`：纯函数、无 IO，与
   `brass-domain` 同构（createMatch / applyCommand / projectForSeat /
   planAutoDecision）。

2. **官方牌表数据经过交叉核对后固化**：
   - 发展卡 90 张：bouk/splendimax 与 seal256/splendor 两个独立数据集
     （列序互异）逐卡比对完全一致，予以采信；boardgamers/splendor 的
     data.ts 与两者大面积冲突（其 1 分牌成本破坏了官方牌表「五色成本
     构成置换」的结构性规律），判定为转录错误，不采信。
   - 贵族 10 张：官方构成为 5 张 4+4 + 5 张 3+3+3（无 3+3 型，BGG/Fandom
     资料核验）；采信 boardgamers 名单（其 4+4 五张与 machow/splendid
     完全一致，3+3+3 型亦经 Geeky Hobbies 等资料印证）。
   - 规则语义以官方规则书 PDF（Space Cowboys 2014）为准：明牌被购/预留
     立即同级补位、筹码 10 枚上限即时弃牌、贵族每回合至多一位且不可拒、
     15 分后「complete the current round」。

3. **命令保持原子**（延续 ADR-0009 决策 2）：take_gems / reserve_table /
   reserve_deck / purchase_table / purchase_reserved / discard_gems /
   choose_noble 七种，一次提交整段行动。购买支付无需玩家显式指定——
   加成优先抵扣、黄金补差是唯一合法解，由引擎确定性计算。

4. **回合收束状态机**：行动 → （超 10 枚则 await_discard）→（贵族判定：
   恰一位自动造访，多位则 await_noble）→ 轮转；finalRound 由 15 分触发，
   轮转回到触发者即结算。弃牌完成后必须回到完整收束流程（贵族判定不可
   跳过）——此点曾有实现偏差，被单测「弃牌后贵族判定」锁定。

5. **服务端三件套**：`splendorRuntime`（座位视图/提交/自动代打）、
   `splendorStore`（`splendor_rooms`/`splendor_runs` 两表，与 brass 同构）、
   `splendorModule`（GameModule 适配器）。决策逐命令落库
   （`submitDecision` 接 `options.store`），沿用 brass 的持久化回归教训。

6. **前端独立视觉体系**（`apps/web/src/splendor/`）：文艺复兴珠宝主题，
   与 coup（宫廷暗色）、brass（工业黄铜）刻意不统一；传输层复用
   `platform/roomApi.ts` 的 `createRoomClient("splendor")`，仅保留文案
   映射与类型。

7. **部署注意**：新增 workspace 包（`@coup/splendor-domain`）后，服务器
   首次部署该版本需 `npm install`（或 `npm ci`）重建 node_modules 链接，
   仅 `npm run build` 不会新建 workspace 符号链接。

## 后果

- 三款游戏共用同一份房间栈与集成测试模式，`splendorRoomApi.test.ts`
  复制 brass 的测试骨架（建房→占座→开局→决策→重启恢复→续局门禁）。
- 测试基线 248 → 272（splendor-domain 18 + server 6）。
- 引擎的「确定性种子 + 纯函数」使超时代打（planAutoDecision）与人类
  决策走同一 submitDecision 通路，无旁路。
