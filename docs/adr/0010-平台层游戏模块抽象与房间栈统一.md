# ADR-0010：平台层 GameModule 抽象与房间栈统一

日期：2026-09-05 ｜ 状态：已接受

## 背景

ADR-0009 曾决策：第三款游戏出现前，不强行抽象 GameModule——coup 与 brass 的决策模型差异过大（coup=单步决策流；brass=原子复合命令）。第三款游戏（Splendor / Love Letter 等候选）已进入规划，现在到了兑现这一步的时候。

落地前盘点两栈重复度：`apps/server` 中 coup 内联路由（createApp.ts 约 1700 行）与 brass 平行栈（brassRoutes.ts 约 900 行）在以下方面近乎逐行克隆：

- 房间 CRUD / 占座 / 改名 / 座位开关 / 房间设置 / 开局门禁
- 心跳离席状态机接线、回席轮换凭证、房主处置
- 回合计时器与超时代打（含缺席顺延、重启重排）
- 增量轮询（`since`/`spectate`）、决策提交、终局清场
- 续局三端点、重启恢复清单与放弃、空房回收与清扫
- 两套几乎同构的 SQLite 持久化（rooms + runs）

克隆已经产生了两个真实的线上级缺陷（均无测试覆盖，只在真人联机时才会踩到）：

1. **brass 决策不落库**：`brassRoutes` 调 `submitBrassDecision` 时漏传 persistence，开局后的所有命令只进内存，服务器重启即回滚到初始局面。
2. **brass 续局路由断裂**：服务端 `/rematch/join`（无 `:seatId` 段）与客户端 `/rematch/join/${seatId}` 路径不一致，且处理函数读取不存在的 `params.seatId`，续局确认永远失败。

## 决策

1. **平台栈收敛为一份实现** `apps/server/src/platform/`：
   - `gameModule.ts`——`GameModule` 接口，即平台与游戏之间的唯一接缝；
   - `gameRoomStack.ts`——按 `GameModule` 参数化的通用房间/对局栈工厂（路由、计时、恢复、回收、续局、轮询）。
2. **`GameModule` 只回答「规则是什么」**：怎么开局（`startMatch`）、谁欠决策（`activeDecidingSeatId`）、命令怎么校验提交（`submitDecision`，允许异步）、状态怎么投影（`seatView`/`spectatorView`）、超时代打（`planAutoDecision`）、座位事实（`seatFacts`：本地/远程/淘汰）、邀请载荷与建房约束。**不统一两游戏的决策模型**——命令载荷类型由各游戏私有，平台按不透明 `payload` 透传，与 ADR-0009 的判断一致。
3. **游戏接入层** `apps/server/src/games/`（coup）与 `apps/server/src/brass/brassModule.ts`（brass）：各约 200 行适配器，包装既有 domain/runtime/store；`matchStore`/`brassStore`/`roomStore` 经薄适配满足 `GameMatchStore`/`GameRoomPersistence` 接缝，表结构不变（零数据迁移）。
4. **createApp 只留应用外壳**：会话/CSRF/Origin 白名单、主机模式、静态资源；两款游戏各用一次 `createGameRoomStack(app, deps, module)` 挂载（coup 路径 `/api/rooms…` 与恢复端点原样保留，brass 保持 `/api/brass/rooms…`）。
5. **前端传输层收敛** `apps/web/src/platform/roomApi.ts`：会话/CSRF 引导 + `createRoomClient(prefix)` 端点工厂；`lanRoom.ts` 与 `brassApi.ts` 退化为「文案映射 + 游戏类型」的薄壳。视觉层不合并（ADR-0009 决策 4 维持：两款游戏视觉独立）。
6. **游戏专属行为用显式钩子，不用布尔旗标堆砌**：`beforeStart`（brass 自动关闭空位 + 座位连续性校验）、`hostForceEliminate`（coup 强制揭示淘汰；brass 不提供 → 平台回 `disposition_not_supported`）、`invitePayload`、`createRequiresLanHost`/`throttleRoomLookup`/`recoveryListKey` 等少量元数据。
7. **统一即修正**：以 coup 栈语义为基准合并后，brass 顺带获得原本缺失的门禁——续局需 run 已结束（`match_in_progress`）、开局走 `requireSession`、恢复清单含 rematch 阶段校验、决策持久化失败折算 `technical_abort`+502（与 coup 同通路）。同时补上 brass 的座位连续性校验（`seats_not_contiguous`）：brass 以玩家序号映射座位（前端硬编码 seatId=序号+1），非连续占座（关闭 2 号后占 3、4 号）会错位绑定，旧实现静默错配，现在显式拒绝。

## 后果

- `brassRoutes.ts` 删除（907 行）；`createApp.ts` 由 1712 行减至约 300 行。
- 新增游戏的最小接入面：一个 `GameModule` 适配器（约 200 行）+ 前端桌面 UI + `createApp` 一行挂载 + 一份 API 集成测试；房间编排、计时、离席、恢复、续局、轮询、持久化接缝全部复用。清单见 `docs/platform/adding-a-game.md`。
- coup 的 91 项集成测试不加改动地跑在通用栈上（仅恢复清单新增 `game` 字段一处断言更新），证明抽象以既有行为为基准；brass 新增 7 项 API 集成测试锁定上述两个缺陷的回归。
- brass 开局后决策逐命令落库（`brassStore.commitCommand`），重启不再回滚。
- `packages/domain`、`@coup/brass-domain`、`@coup/protocol`、`@coup/web-desk` 均零改动；本机版（server-local/web-local）零纠缠。
